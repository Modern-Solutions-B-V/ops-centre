## Boundaries

- Native host Ollama remains the inference path.
- QR1 does not bind Ollama to `0.0.0.0`; containers reach it through `ms-qr1-host:<MS_QR1_HOST_GATEWAY>`, which points at the actual non-internal ODS Docker gateway where the host-side HTTP bridge listens. The systemd unit executes the installed root-owned bridge copy under `/usr/local/libexec/ms-qr1/`, not mutable checkout code. The bridge forwards only to `127.0.0.1:11434`, rewrites upstream `Host` to `localhost:11434`, preserves streaming Ollama responses with incremental reads, streams request bodies upstream in bounded slices, caps request bodies at 256 MiB by default, closes truncated fixed-length upstream responses promptly, and uses a 300 second upstream timeout by default.
- QR1 pre-start provisioning must run before any `docker compose up`, including `up --no-start`, because Compose creates containers and evaluates bind mounts before starting services.
- `data/persona/SOUL.md` is generated by `scripts/build-installation-context.py` before Hermes can evaluate its file bind mount, then refreshed after stack startup through `scripts/ms-qr1-prestart-provision.sh poststart-refresh`; `data/persona` and `data/persona/SOUL.md` must not be symlinks during privileged provisioning.
- `data/n8n` ownership is corrected only for that directory tree, using the effective rendered n8n UID/GID from Compose; directory and file modes are normalized separately before first start, runtime checks allow n8n-created read bits while still rejecting missing owner-write, group/world-write, symlinks, wrong owners, and unexpected file types, and no broad `data/` chown or world-writable permission is part of QR1.
- UFW rules are scoped from non-internal Docker CIDR(s) to their matching Docker gateway on TCP `11434` and `7710`; the internal Langfuse network is excluded.
- The host-agent systemd service is a required QR1 host prerequisite because the approved trust matrix includes dashboard-api host-agent access on `7710`.
- No AMD tuning, UMA/GTT/IOMMU, Lemonade, email, Jira, client-system credentials, production secrets, ODS Tailscale extension, ods-proxy, Brave Search, OpenClaw, ODS OpenCode extension, remote-provider egress service, or remote-provider SSH tunnel are enabled.
- `model-router` remains present in the rendered QR1 stack as an inert/internal core service: it publishes no port and its configured endpoint points only at excluded `llama-server:8080`, so it is not a QR1 egress path.
- Hermes dashboard TUI is forced off with `HERMES_DASHBOARD_TUI=0`.
- Qdrant and SearXNG require non-empty generated secrets.
- Host-agent nmcli routes have no supported disable switch in upstream config; QR1 documents and tests unauthenticated denial instead of editing core host-agent code.
- LiteLLM scoped virtual consumer keys are deferred to QR2. QR1 shares the LiteLLM master key with Open WebUI and Hermes because there is no clean CONFIGURE-only virtual-key provisioning path in this ODS profile without adding deployment complexity or touching core code.
- Clean Ubuntu 24.04 deploy hosts must have `python3-yaml` and `jq` before QR1 validation; `jq` is required by `scripts/validate-env.sh`.
